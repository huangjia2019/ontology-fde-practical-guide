# FDE 现场练习：从一笔业务开始

一本书和一个仓库，可以让我们练习怎样核实事实、建立对象、限定动作，再检查执行结果。到企业现场，还会遇到数据拿不到、几个部门理解不同、旧系统没有合适接口、责任人没有时间参与。这些工作也属于 FDE。

下面按云帆项目的推进顺序安排练习。每一步需要什么人、留下什么材料、怎样知道还不能继续，都值得亲自走一遍。现场的数据、接口和参与人员不同，推进时间需要与客户一起确定。

## 一、跟着业务人员处理一笔申请

先读[“遥控器单”的走查记录](artifacts/01-field-walkthrough.md)。客服查了订单、签收、工单、视频和风控，最后停在发票查询上：系统说“本次未查到记录”，财务还没有确认“未开票”。

在自己的项目中，请业务人员挑一笔近期发生的、允许用于项目讨论的业务。让他按平时的顺序处理，你记录每一次切换系统、找人和等待。不要急着把他说的话写成规则；问一问这笔和上一次为什么不同。

走查后留下[项目定位卡](artifacts/01-ontology-positioning-card.md)：要改善哪段工作、围绕哪个对象、先允许哪些动作、哪些情况必须找人。办理耗时、转人工比例等目标，需要先确认当前基线和统计方法。仓库没有替企业测量这些数字。

本地练习：

```bash
python3 run.py inspect YF-R-0311
```

请客服核对对象和办理过程，请财务核对发票结论。找不到事实来源时，先把它登记为待确认，不替业务人员猜一个答案。

## 二、让几个部门对同一笔业务有共同理解

“订单”可能指交易订单、出库单或合同中的采购项。“退款成功”也可能只是提交了申请。把这些差别放到同一笔案例里讨论，比请大家一次性定义整个企业的术语更容易开始。

参考[最小本体](artifacts/04-minimum-ontology.md)，形成对象目录、关系、状态、术语表和来源映射。每个关键字段指定权威来源与负责人；跨系统编号保留映射。源数据更新得多快、多久需要重新查，也要由业务容忍度和接口能力一起决定。

```bash
python3 run.py graph --refund-id YF-R-0311
```

请试着沿 `RefundRequest → Order → OrderItem` 找到退款商品，再查证据支持的是哪笔申请。到了现场，图能连起来只是开始，还要请数据负责人确认连得对不对。

## 三、把可以做的动作交给程序检查

请业务专家拿出几笔“看起来差不多，处理却不同”的申请：500 元与 500.01 元、低金额黑名单客户、合同客户、已开票订单、付款失败。分别问：什么条件变了，谁因此需要接手？

将判断整理为[规则草稿](artifacts/06-rule-assets.md)，将业务动作整理为[动作契约](artifacts/05-action-contract.md)。契约要写出前提、效果、批准权、重试方式与失败处理。能生成一份建议，与有权批准退款，是两项不同的验收。

```bash
python3 run.py run YF-R-0500 --mode draft
python3 run.py run YF-R-0501 --mode draft
python3 run.py evaluate
```

让财务和客服主管先看建议及依据，再讨论自动化范围。本地评估通过，只说明这些样例符合预期。新企业还需要自己的例外案例、失败案例和经业务确认的预期答案。

## 四、演练写入、失败和人工接手

```bash
python3 run.py run YF-R-0500 --mode write
python3 run.py run YF-R-0800 --mode write \
  --simulate-payment-failure --audit artifacts/payment-failure.jsonl
```

第一笔创建模拟付款指令。第二笔在批准后创建付款指令失败，状态为 `approval_pending_payment`，并生成财务处理任务。请财务回答：看到这份任务，是否知道已经发生什么、还需要做什么、怎样避免重复付款？

权限也要反着试：把执行主体换成未登记的 Agent，使用过期委托，重复提交同一业务意图。相应行为由[执行器测试](../tests/test_engine.py)覆盖。同一进程内的幂等演示不等于跨机器、跨重启的交易保证；真实接口需要持久化、并发控制和对账方案。

## 五、把项目交还给组织

交接时请接管人员操作，你在旁边看：查一笔决策、运行一组回归、判断一次失败应该交给谁。操作失败的地方就是交接仍缺的东西。流程、规则和权限的变更各由谁批准，也要落实到岗位。

[运行交接卡](artifacts/10-operations-handoff-and-replication.md)包含一套退出演练：关闭写入、撤销凭据、交还未完成工作、保存证据、验证人工业务还能继续。仓库只做离线演练，不会撤销真实账号或搬移真实工单。

```bash
python3 run.py exit-drill
```

复制到第二个场景时，复用经过验证的结构，重新确认业务含义。退款里的“批准”，换到销售跟进、采购或科研项目中，会有不同的责任和后果。

## 一页现场笔记

| 记录项 | 写下什么 |
|---|---|
| 业务与对象 | 哪笔业务、当前状态、希望改善哪一段 |
| 观察 | 谁做了什么，查了哪里，等了谁 |
| 分歧 | 哪两个说法不一致，哪项证据还缺失 |
| 判断 | 根据什么条件，建议做什么或在哪里停下 |
| 责任 | 谁确认事实、谁批准动作、失败后谁接手 |
| 验证 | 哪个样例和测试能证明判断成立 |
| 下一次回访 | 待确认事项、负责人、约定时间 |

先把一笔业务走通，再逐步扩大范围。实践过程中对人、行业和组织形成的理解，会决定下一版模型该保留什么、补上什么。
