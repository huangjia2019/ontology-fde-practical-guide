# 第 10 站：项目组离开之后，谁继续处理

把代码交出去，还没有回答谁能改规则、谁看失败记录、谁接手未完成退款。请接管团队亲自运行一次正常案例、一次故障和一次退出演练，把做不下去的地方记下来。

## 本地交接练习

```bash
python3 tools/verify.py
python3 run.py demo --output artifacts/demo
python3 run.py exit-drill
python3 run.py checkpoint 10 --check
```

`demo` 将读取、建议和几条写入分支放在一次进程中演练，生成运行结果、决策记录、对象图、评估报告和规则草稿报告。查看输出目录中的 `manifest.json`，再按列出的文件逐一检查。不要把“生成了文件”当成业务验收完成。

`demo` 重新运行时会重建其输出目录中的示例决策记录。需要保留上一轮对照时，请换一个输出目录。

| 接管工作 | 应能完成的操作 | 建议责任岗位 |
|---|---|---|
| 业务处理 | 判断何时转人工，找到待办及失败原因 | 客服运营、财务 |
| 规则变更 | 找到来源、审核人和回归样例 | 业务规则负责人 |
| 版本发布 | 运行测试，核对变更和回退方案 | 平台工程、测试 |
| 权限维护 | 确认授权范围、变更记录和停用入口 | 安全、系统负责人 |
| 日常复盘 | 从错误判断提取新的回放样例 | 业务与技术共同负责 |

这些岗位是交接建议，需要在真实项目中落实到人员和制度。仓库不会代替业务负责人作出上线批准。

## 退出演练

业务负责人撤回授权、替代版本接管或发生严重治理问题时，需要停止 Agent，并保证人工还能继续办理。

1. 关闭写入（Close `Write`）：停用新业务写入，保留必要查询。
2. 撤销凭据（Revoke credentials）：确认需要撤销的工作负载身份、密钥和工具授权，由身份管理负责人执行。
3. 交还未完成工作（Return unfinished work to people）：将未完成退款、待人工审批和 `approval_pending_payment` 交给客服或财务。
4. 保留审计证据（Preserve audit evidence）：保留身份版本、权限快照、契约、规则、决策与事故记录。
5. 验证业务连续性（Verify business continuity）：由人工渠道处理一笔测试业务，检查停用主体是否仍有写入。

`exit-drill` 检查相关配置、文档和交接信息，输出五步状态。预期 `status: PASS`，同时 `scope` 表明没有真实 IAM 或 ERP 变更。这是离线交接演练，未执行实际凭据撤销或真实工单迁移；现场演练要有各系统的执行回执。

## 第二个场景复用哪些东西

假设下一项工作是销售机会跟进，先逐项比较，不直接复制退款规则。

| 可以复用的结构 | 必须重新建模或确认 |
|---|---|
| 来源引用、对象编号映射 | 销售机会、联系人、跟进状态与字段含义 |
| 独立身份和六维权限检查思路 | 新身份、负责人、授权范围与真实凭据 |
| 动作契约、幂等与补偿设计 | 创建跟进任务等实际动作及其后果 |
| 规则来源、草稿审核和边界样例 | 销售判断依据、合同约束与业务案例 |
| 委托信封与冲突记录 | 与法务、风控的委托范围和裁决方式 |
| 决策记录与评估结构 | 新场景预期结果、事故回放和收益指标 |

退款引擎有专门的 Python 判断与适配逻辑。第二个场景需要自己的实现，不能只改几个配置名就算迁移完成。

若停用后未完成任务找不到接收人，交接尚未完成；若撤销凭据后仍有写入，应调查旁路接口、共享账号和残留任务。请业务、财务、安全和运维一起确认退出结果。
